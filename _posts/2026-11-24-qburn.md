I've been trying to become more aware of the theory and practice of transformers and LLMs, not just as a consumer of chatbots and coding assistants, but as someone who can train and build such systems. As part of this discovery process, given my background in computer vision and my fondness for the [Burn] ML framework, I decided to port over a vision-language model. I also wanted it to be able to run as a demo on a static website, as I've done with some of my other [projects](/projects/). So, spoiler, it works, and you can try it at the [demo site](/qburn/), but for additional backstory, read on below.

### More than Words

When I started this project, I wanted to answer a fairly specific question: could I take a transformer-based<span class="tooltip-trigger" title="That's going to be most of them, but in computer vision, we still love our convolutional models.">*</span> vision-language model, translate it to Burn, and run that same implementation both as a native Rust program and in a web browser?

The model that I found to help me answer this question is [Qwen3-VL-2B-Instruct]. It's powerful, popular, and open source, and for its input, it accepts text, images, and even video. That makes it a more interesting test than a standalone language model or image classifier.

Qwen3-VL works by joining a vision encoder with a language model to interpret images and generate text. At a high level, the vision encoder turns an image into visual features, which are combined with the text prompt and passed to the language model. The model then generates its response one token at a time, using both the words in the prompt and information from the image.

The connection is actually a bit more involved than a single image embedding. There's a _DeepStack_ feature that also passes certain intermediate visual features into early language-model layers, allowing image information to influence generation at multiple stages.

With my model selected, combining _Qwen_ with _Burn_ gave me the project name: _qburn_.

### More than Weights

Typically, ML models are built and trained in PyTorch. This includes the architecture itself, which is defined in Python code, and the resulting weights, which are saved as a separate file. For inference, though, the model is often exported to ONNX, which combines both the architecture and weights into a single file. This makes it easier to use, and ONNX is widely supported and very optimized, though it's less flexible. Burn is a bit more like PyTorch, in that the model architecture is defined in the code, and the weights are loaded from a file at runtime. So, if you want a model in Burn, you can either import the architecture from an ONNX file to autogenerate that code, or it can be transcribed layer-for-layer. With coding assistants, the latter option is easy, and doing this direct translation keeps flexibility that is commonly lost when models are exported to ONNX from PyTorch.<span class="tooltip-trigger" title="For instance, in the Burn model, the image is optional, which allows for real text-only input, whereas the ONNX version requires a placeholder image.">*</span>

In this project, the original weights (as _safetensors_) are downloaded from Hugging Face, converted to _burnpacks_, and re-uploaded to Hugging Face. There are also pre-existing ONNX versions of the model available there. A static webpage can then load any of these weights like any other remote asset.

### One Crate, Multiple Environments

With the model layers transcribed, the weights converted from _.safetensors_ to _.bpk_ format, and some pre- and post-processing added, the model is ready to run. One of the great things about Burn is how portable it is. The same code can run on different operating systems, on different hardware with various accelerators, and even in the browser.

On the command line, I can load a model and ask it to describe an image, compare multiple images, or sample frames from a video. Native builds can use backends such as Metal or CUDA, or even just CPU, which makes the CLI a quick, convenient, and practical way to run repeated experiments, without resorting to more powerful cloud infrastructure.

The browser version compiles the same model code to WebAssembly and runs it locally with WebGPU. A web worker owns the model so that inference does not freeze the page, and generated tokens stream back to the interface as they arrive. However, in this case, there is no CPU fallback; the browser needs WebGPU support and enough memory for the model. These constraints are expanded upon below, but because the model is running up against them and doesn't have access to the same accelerators, it's much slower than the CLI or other more optimized approaches.

### Making It Fit

The original model checkpoint, which is about 4 GiB, is too large to fit in the browser demo, as there's a 2 GiB WebAssembly limit that I had to work with. To fit the model, the _qburn_ converter includes the ability to quantize the weights. This reduces their precision to make them smaller, going from float32 to float16, or even down to four-bit precision, while hopefully not reducing accuracy too much. Ideally, this would be done as part of training to minimize accuracy loss, versus the post-training quantization done in this case.

For the browser demo, I use a mixed quantization setup. The large linear layers use four-bit weights, while parts where precision matters more stay in half precision. The resulting pack is still large, so it is split into shards and loaded from a manifest rather than committed to the repository. This is a practical compromise: smaller downloads than the original checkpoint, while keeping more precision in the sensitive parts of the model than uniform four-bit quantization would.

GitHub itself also has a file limit of 100 MiB for non-LFS files (and LFS doesn't work with GitHub Pages), which is why the converted models had to go back to Hugging Face as a place to host them.

There are other constraints with the web demo as well, such as having to omit fusion and autotune, as well as a WebGPU shared memory limit that affects tile size when doing matrix multiplication operations.

Including video processing makes the resource tradeoffs especially visible. More frames provide more temporal context, but the model has a fixed pixel budget across time and space. As the frame count goes up, each frame has to become smaller. The browser demo therefore samples only four frames for a video, while the CLI allows more control when temporal coverage matters more than image detail.

### Alternatives

At the demo site, there are actually two demos: one based on Burn and another on [transformers.js]. This is a library specifically designed for running pre-trained machine learning models directly in web browsers. Therefore, it is a lot more optimized for that environment than anything I can produce with Burn at the moment. This won't necessarily be true in the long term, but it certainly is for now. Likewise, the ONNX-exported version of the model contains optimizations not present in the Burn model.

Most large models, by contrast, don't run locally at all. They are usually hosted on a server in a data center, and a website or application is simply making API calls to that powerful (and expensive) hardware. This is a very fast and convenient approach. However, it requires reliable Internet access and is subject to the whims of the model provider (rate limits, token costs, content filters, etc.).

### Conclusions

Getting a VLM to run locally and produce reasonable text is relatively straightforward these days. Adding on a browser demo to that same codebase opened up a series of new questions and challenges along the way. This is not a polished replacement for a hosted service, nor is it even the most efficient browser implementation. It is a working path through a surprisingly long chain of model code, GPU kernels, quantized weights, WebAssembly, and browser APIs.

There is still plenty of room to improve speed and broaden the testing, but the central experiment works: the same Burn model implementation can run on a native backend and in a browser through WebGPU.

I encourage you to check out the [demos](/qburn/), read the notes there, and visit the [repo] to run it yourself.
